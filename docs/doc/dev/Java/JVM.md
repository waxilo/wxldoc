## 类加载

### 加载

- 通过类的全限定名获取定义类的二进制字节流
- 将字节流所代表的静态存储结构转化为方法区的运行时数据结构
- 在内存中生成代表这个类的 java.lang.Class 对象，作为方法区这个类的各种数据的访问入口
> 注：该 `java.lang.Class` 对象**本体位于堆中**，其生成动作属于加载阶段；它仅作为方法区类元数据的访问入口，并非本身在方法区。详细归属见下方「对象与类在哪里分配」。

### 链接

#### 验证
- 文件格式验证：验证字节流是否符合 Class 文件格式规范
- 元数据验证：对字节码描述的信息进行语义分析
- 字节码验证：通过数据流和控制流分析确定程序语义是合法、符合逻辑的
- 符号引用验证：确保解析动作能正常执行

#### 准备
- 为类变量分配内存并设置类变量初始值（零值）
- 这些变量使用的内存：JDK 7 及之前在方法区（永久代）分配；JDK 8 起移至 Java 堆（作为 Class 对象的一部分），方法区（元空间）仅存类元数据。
- 不包含实例变量，实例变量将会在对象实例化时随对象一起分配在 Java 堆中

#### 解析
- 将常量池内的符号引用替换为直接引用
- 主要针对类或接口、字段、类方法、接口方法等类型

### 初始化
- 执行类构造器 `<clinit>()` 方法
- `<clinit>()` 是由编译器自动收集类中所有类变量的赋值动作和静态语句块中的语句合并产生的
- 父类的 `<clinit>()` 先执行，再执行子类的
- 虚拟机会保证 `<clinit>()` 方法在多线程环境中被正确地加锁、同步

## 运行时数据区

| 区域       | 共享  | 作用                              | GC  |
| -------- | --- | ------------------------------- | --- |
| 堆        | 共享  | 存放对象实例。                         | 会   |
| Java虚拟机栈 | 私有  | 存储调用的方法，每个方法作为一个栈帧。             | 会   |
| 本地方法栈    | 私有  | 存储调用的native方法，每个native方法作为一个栈帧。 | 会   |
| 计数器      | 私有  | 记录CPU执行位置，提供线程切换能力。             | 不会  |
| 方法区      | 共享  | 存储已被加载的类的结构信息：类元数据、运行时常量池、JIT 代码缓存（JDK 8 前还含静态变量，JDK 8+ 静态变量移至堆）。 | 会   |

## 对象与类在哪里分配

"类对象"在 Java 里常指三种不同的东西，分配位置完全不同：

| 你指的 | 是什么 | 分配在哪里 |
| --- | --- | --- |
| 类的实例对象 | `new Foo()` 出来的普通对象实例 | **堆（Heap）** |
| Class 对象 | `Foo.class` / `obj.getClass()`，即 `java.lang.Class` 的实例 | **堆（Heap）** |
| 类元数据 | Class 对象背后承载的类结构数据（类型信息、方法字节码、运行时常量池等） | **方法区（JDK 8+ 是元空间 Metaspace）** |

要点：
- 普通实例对象不在方法区，在堆；只有引用（局部变量/参数）在栈上，对象实体一律在堆。
- Class 对象本身也不在方法区，它就是一个普通的 Java 对象，在堆上；只是它"指向"的那份类元数据存放在方法区（元空间）。
- 真正躺在方法区里的是"类元数据"，不是对象本身。

### 方法区存什么
方法区是 JVM 规范定义的逻辑分区（不是物理内存块），存储已被加载的类的结构信息：
- 类的元数据：全限定名、父类、接口、字段、方法、访问修饰符等
- 运行时常量池（Runtime Constant Pool）
- 方法字节码、JIT 编译后的代码缓存

### JDK 8 的变化（易踩坑）
- JDK 7 及之前：方法区实现为"永久代（PermGen）"，静态变量（static 字段）在永久代。
- JDK 8 及之后：废除永久代，改为**元空间（Metaspace，使用本地内存 Native Memory）**；同时**静态变量被移到堆里**，作为 Class 对象的一部分存放。

> 结论：对象实例和 Class 对象都在堆；方法区只放"类的描述信息"（元数据），而且 JDK 8 之后连静态变量都从方法区挪到了堆。不要把"方法区存类信息"误解成"方法区存类对象"。

## 可达性算法

### GC Root
1. 方法区中类静态属性引用的对象
2. 方法区中常量引用的对象
3. 虚拟机栈中引用的对象
4. 本地方法栈中 JNI（Native 方法）引用的对象
5. 所有被同步锁（synchronized 关键字）持有的对象
6. JVM 内部的引用（基本类型对应的 Class 对象、常驻异常对象、系统类加载器）
7. 反映 JVM 内部情况的 JMXBean、JVMTI 中注册的回调、本地代码缓存等

### 三色标记

1. **白色**：表示对象尚未被垃圾收集器访问过
2. **灰色**：表示对象已经被垃圾收集器访问过，但这个对象上至少存在一个引用还没有被扫描过
3. **黑色**：表示对象已经被垃圾收集器访问过，且这个对象的所有引用都已经扫描过

#### 三色标记的问题
- **漏标**：原本应该被标记为存活的对象被标记为死亡
- **多标**：原本应该被标记为死亡的对象被标记为存活

#### 解决方案
- **增量更新（Incremental Update）**：黑色对象一旦新插入了指向白色对象的引用之后，它就变回灰色对象（CMS 采用）
- **原始快照（Snapshot At The Beginning, SATB）**：当灰色对象要删除指向白色对象的引用关系时，就将这个要删除的引用记录下来，扫描结束后，以这些记录的引用对象作为根再扫描一次（G1、Shenandoah 采用）



## 垃圾回收算法

### 标记清除法（Mark-Sweep）

**原理**：
1. 先标记出所有需要回收的对象
2. 统一回收所有被标记的对象

**优点**：
- 实现简单

**缺点**：
- 效率不稳定（如果需要回收的对象多，效率低）
- 会产生大量不连续的内存碎片，空间碎片太多可能会导致以后在程序运行过程中需要分配较大对象时，无法找到足够的连续内存而不得不提前触发另一次垃圾收集动作

### 标记复制法（Copying）

**原理**：
1. 将可用内存按容量划分为大小相等的两块
2. 每次只使用其中的一块
3. 当这一块的内存用完了，就将还存活着的对象复制到另外一块上面
4. 然后再把已使用过的内存空间一次清理掉

**优点**：
- 不会产生内存碎片
- 实现简单，运行高效

**缺点**：
- 将内存缩小为原来的一半，空间浪费较大
- 对象存活率较高时就要进行较多的复制操作，效率会变低

**应用场景**：
- 新生代，对象存活率低

### 标记整理法（Mark-Compact）

**原理**：
1. 标记过程与标记清除法相同
2. 让所有存活的对象都向一端移动
3. 然后直接清理掉端边界以外的内存

**优点**：
- 不会产生内存碎片
- 空间利用率高

**缺点**：
- 需要移动对象，成本较高

**应用场景**：
- 老年代，对象存活率高



## 垃圾回收器

### 串行回收器（Serial）

**特点**：
- 单线程工作
- 进行垃圾收集时必须暂停其他所有的工作线程（Stop The World）
- 简单高效，对于限定单个 CPU 的环境来说，Serial 收集器没有线程交互的开销，专心做垃圾收集可以获得最高的单线程收集效率

**适用场景**：
- 客户端应用
- 单核 CPU 环境

### 并行回收器（Parallel Scavenge）

**特点**：
- 多线程收集
- 目标是达到一个可控制的吞吐量（Throughput）
- 吞吐量 = 运行用户代码时间 / (运行用户代码时间 + 垃圾收集时间)

**适用场景**：
- 注重吞吐量的后台运算任务

### G1回收器（Garbage-First）

**特点**：
- 面向服务端的垃圾收集器
- 基于 Region 的内存布局，把堆分成多个大小相等的独立区域
- 可以建立可预测的停顿时间模型
- 整体上看是基于标记整理的收集器，局部上看是基于复制算法

**优势**：
- 可预测的停顿时间
- 空间整合，不会产生碎片
- 并行与并发
- 分代收集

**G1 收集过程**：
1. 初始标记（Initial Marking）：STW，标记 GC Roots 能直接关联到的对象
2. 并发标记（Concurrent Marking）：与用户线程并发执行
3. 最终标记（Final Marking）：STW，修正并发标记期间因用户程序继续运作而产生变动的那一部分标记记录
4. 筛选回收（Live Data Counting and Evacuation）：STW，根据用户期望的停顿时间来制定回收计划

### 其他组合

#### ParNew 新生代回收

- Serial 收集器的多线程版本
- 除了 Serial 收集器外，只有它能与 CMS 收集器配合工作
- 在单 CPU 环境下不会比 Serial 收集器有更好的效果

#### CMS 老年代回收（Concurrent Mark Sweep）

**目标**：获取最短回收停顿时间

**收集过程**：
1. 初始标记（Initial Mark）：STW，标记 GC Roots 能直接关联到的对象
2. 并发标记（Concurrent Mark）：与用户线程并发执行
3. 重新标记（Remark）：STW，修正并发标记期间因用户程序继续运作而产生变动的那一部分标记记录
4. 并发清除（Concurrent Sweep）：与用户线程并发执行

**优点**：
- 并发收集，低停顿

**缺点**：
- 对 CPU 资源敏感
- 无法处理浮动垃圾
- 使用标记清除算法，会产生空间碎片

#### Parallel Old

- Parallel Scavenge 收集器的老年代版本
- 使用多线程和标记整理算法
- 与 Parallel Scavenge 配合使用，注重吞吐量

#### Serial Old

- Serial 收集器的老年代版本
- 单线程收集器
- 使用标记整理算法
- 主要作为 CMS 收集器的后备预案
