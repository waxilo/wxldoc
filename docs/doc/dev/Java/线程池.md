## 7大参数

```java
public ThreadPoolExecutor( 
	int corePoolSize, // 核心线程数 
	int maximumPoolSize, // 最大线程数 
	long keepAliveTime, // 空闲线程存活时间 
	TimeUnit unit, // 时间单位 
	BlockingQueue<Runnable> workQueue, // 任务队列 
	ThreadFactory threadFactory, // 线程工厂 
	RejectedExecutionHandler handler // 拒绝策略 
)
```

## 执行流程

1. 新增任务，如果核心线程池未全部创建，不进入任务队列，创建线程直接执行；如果核心线程池已全部创建，进入任务队列。
2. 当队列已满，创建临时线程来消费任务；当临时线程空闲达到规定时间会被销毁。
3. 如果队列已满，触发拒绝策略。

## 任务队列
| 队列类型                    | 特点                         | 适用场景                              |
| ----------------------- | -------------------------- | --------------------------------- |
| `ArrayBlockingQueue`    | 有界队列（需指定容量）                | 控制内存，防止 OOM                       |
| `LinkedBlockingQueue`   | 无界队列（默认 Integer.MAX_VALUE） | 任务量平稳，但可能 OOM                     |
| `SynchronousQueue`      | 不存储任务，直接交给线程               | 高吞吐、快速响应（如 `newCachedThreadPool`） |
| `PriorityBlockingQueue` | 优先级队列                      | 任务有优先级                            |

### SynchronousQueue 详解

`SynchronousQueue` 是一个**不存储任何元素的阻塞队列（容量为 0）**。在线程池中用它做任务队列时，效果是**任务不排队，直接"交接"给线程**——有空闲线程就交给它，没有就立刻新建线程，直到达到最大线程数；再不够就直接触发拒绝策略。它是一种"直接提交"（direct handoff）策略，而非"缓冲"策略。

提交任务时的判定顺序：

| 步骤 | 条件 | 结果 |
| --- | --- | --- |
| 1 | 有空闲线程（含核心线程） | 直接交给空闲线程执行 |
| 2 | 无空闲线程，且当前线程数 < maximumPoolSize | 立即新建线程执行 |
| 3 | 无空闲线程，且当前线程数 == maximumPoolSize | 触发拒绝策略 |

关键点：永远不会走到"队列里"这一步。`SynchronousQueue.offer()` 要么立刻被等待的消费者拿走（返回 true），要么立刻失败（返回 false），不会把任务存下来。因此任务堆积只可能表现为**线程数暴涨**，而不是队列变长。

**参数设置要点**：因为队列不缓冲、任务全靠新线程承接，如果 `maximumPoolSize` 设得太小，稍微一并发就拒绝；通常要配较大的 `maximumPoolSize`（如 `newCachedThreadPool` 用 `Integer.MAX_VALUE`），并配合合理的拒绝策略（如 `CallerRunsPolicy` 让提交方自己跑，起到自然限流）。

**优缺点与适用场景**：
- 优点：任务零延迟入队，提交方不被队列阻塞，响应最快；不会无限制堆积占用内存。
- 风险：并发突增时会疯狂创建线程，CPU 调度和内存开销陡增，必须给 `maximumPoolSize` 设合理上限并配拒绝策略兜底。
- 适用：大量相互独立、执行时间短的异步任务（如轻量 RPC 回调）。
- 不适用：任务重、耗时长或需要削峰填谷（背压）的场景——那种应该用 `LinkedBlockingQueue` / `ArrayBlockingQueue` 做有界缓冲。

## 拒绝策略
| 策略                    | 行为                              |
| --------------------- | ------------------------------- |
| `AbortPolicy`（默认）     | 抛出 `RejectedExecutionException` |
| `CallerRunsPolicy`    | 由提交任务的线程自己执行该任务（同步执行，降低提交速度）    |
| `DiscardPolicy`       | 静默丢弃任务，不抛异常                     |
| `DiscardOldestPolicy` | 丢弃队列中最老的任务，然后重试提交（可能再次失败）    |

## 常见线程池

### newFixedThreadPool

```java
ExecutorService executor = Executors.newFixedThreadPool(nThreads);
```

**特点**：
- 核心线程数和最大线程数相等
- 队列：LinkedBlockingQueue（无界队列）
- 空闲线程不会被回收
- 适合任务量平稳的场景

**问题**：队列无界，可能堆积大量任务导致 OOM

### newCachedThreadPool

```java
ExecutorService executor = Executors.newCachedThreadPool();
```

**特点**：
- 核心线程数：0
- 最大线程数：Integer.MAX_VALUE
- 队列：SynchronousQueue（不存储任务）
- 空闲线程 60 秒后回收
- 适合大量短任务

**问题**：最大线程数太大，可能创建大量线程导致 OOM

### newSingleThreadExecutor

```java
ExecutorService executor = Executors.newSingleThreadExecutor();
```

**特点**：
- 核心线程数和最大线程数都是 1
- 队列：LinkedBlockingQueue（无界队列）
- 保证任务顺序执行
- 线程挂掉会自动创建新线程

**问题**：队列无界，可能堆积大量任务导致 OOM

### newScheduledThreadPool

```java
ScheduledExecutorService executor = Executors.newScheduledThreadPool(corePoolSize);
```

**特点**：
- 支持定时和周期性任务
- 队列：DelayedWorkQueue
- 适合需要定时执行的任务

## 线程池参数配置建议

### CPU 密集型任务
- 核心线程数：CPU 核心数 + 1
- 原因：避免频繁的线程上下文切换

### IO 密集型任务
- 核心线程数：2 × CPU 核心数
- 原因：IO 操作时线程会被阻塞，需要更多线程充分利用 CPU

### 计算公式
```
线程数 = CPU 核心数 × (1 + 等待时间 / 计算时间)
```

## 线程池关闭

### shutdown()
- 平缓关闭，不再接受新任务
- 已提交的任务会继续执行完

### shutdownNow()
- 立即关闭，尝试停止正在执行的任务
- 返回未执行的任务列表

### isShutdown()
- 判断线程池是否已关闭

### isTerminated()
- 判断所有任务是否都已执行完毕

## 线程池监控

- `getPoolSize()`：当前线程数
- `getActiveCount()`：活跃线程数
- `getCompletedTaskCount()`：已完成任务数
- `getQueue().size()`：队列中等待任务数
