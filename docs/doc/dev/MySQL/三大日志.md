**一句话**：三大日志里，只有 **binlog 是"提交时才写进文件"**；**redo log 从事务的第一条修改起就在写**，只是先落在内存 buffer；**undo log 全程都在写**。真正的混淆点不是"什么时候写"，而是"写到内存还是写到磁盘"——这两个动作被 `innodb_flush_log_at_trx_commit` 和 `sync_binlog` 分别管着。

## 三者对比

| 特性      | Redo Log     | Undo Log        | Binlog                        |
| ------- | ------------ | --------------- | ----------------------------- |
| 所属层级    | InnoDB 引擎层   | InnoDB 引擎层      | MySQL Server 层                 |
| 作用      | 崩溃恢复、持久性     | 回滚、MVCC         | 主从复制、PITR                     |
| 日志类型    | 物理日志         | 逻辑日志            | 逻辑日志（可选 ROW/STATEMENT）        |
| 写入时机    | 执行中持续写 buffer | 执行中持续写          | 执行中仅写线程私有 cache                |
| 提交时的落盘  | 按参数刷盘（可 fsync） | 无落盘动作，留着给 MVCC | 写入文件，按参数 fsync                |
| 是否循环写   | 是            | 否（由 purge 清理）   | 否（追加写，可轮转）                    |
| 是否支持事务  | 是            | 是               | 是（通过 2PC 与 Redo Log 协调）       |
| 默认开启    | 是（InnoDB）    | 是（InnoDB）       | 否（需配置 `log_bin`）              |

## 写入时机：先分清 buffer 和文件

### 一句话总览

| 日志        | 事务执行过程中             | 事务提交时                          | 内存载体                         | 控制落盘的参数                        |
| --------- | ------------------- | ------------------------------ | ---------------------------- | ------------------------------ |
| **Redo**  | 每条记录按序写入 redo log buffer | write + fsync，并把事务状态从 prepare 切成 commit | `redo log buffer`，默认 16MB     | `innodb_flush_log_at_trx_commit` |
| **Undo**  | 随每条 DML 持续写入 undo 表空间 | 不删、不动，保留给 MVCC 和回滚           | undo buffer（本身也受 redo 保护）    | 无（由 purge 线程异步回收）               |
| **Binlog** | 只累积在 binlog cache，不碰文件 | 从 cache write 到 binlog 文件，再按参数 fsync | 线程私有 `binlog cache`，默认 32KB   | `sync_binlog`                   |

### 完整时序

```text
事务执行中
  ├─ 修改 Buffer Pool 中的数据页（页变成脏页）
  ├─ 写 Undo Log（这条 undo 记录本身也受 Redo 保护）
  └─ 写 Redo Log Buffer
                │
         用户执行 COMMIT
                │
  ① InnoDB Prepare：Redo Log 刷盘，事务状态置为 prepare
  ② Server 层：binlog cache → binlog 文件，按 sync_binlog 决定是否 fsync
  ③ InnoDB Commit：Redo Log 写入 commit 标记（这一步不需要立即刷盘）
```

### 为什么 redo 不能等提交再写

redo 记录的是"某个数据页发生了什么修改"，它必须**早于脏页刷盘**落定，否则会丢一次修改。事务执行期间，buffer pool 里的页已经被改了，此时如果崩溃，而 redo 还没写下来，这一半的修改既没有日志可以重放，也回不到原始状态——数据页就彻底坏了。

所以 redo 只能在每一次页修改时就跟上去写，这就是 **WAL（Write-Ahead Logging）** 的字面含义：日志先行。

而 binlog 不一样，它按**事务**为单位记录变更，没有"必须早于某次刷脏"的约束，完全可以攒到提交时再一次性写出去。

## Redo Log

### 1. 作用

- **保证事务的持久性（Durability）**。
- 数据库异常宕机时用于**崩溃恢复（Crash Recovery）**，确保已提交事务的修改不丢失。

### 2. 存储位置

- 物理文件，位于数据目录下。
- **MySQL 8.0.30 之前**：`ib_logfile0`、`ib_logfile1`，文件数与大小由 `innodb_log_files_in_group`、`innodb_log_file_size` 控制。
- **MySQL 8.0.30 及之后**：改为 `#innodb_redo/` 目录下的 32 个 `#ib_redo*` 文件，总容量由 `innodb_redo_log_capacity` 控制（默认 100MB）。`innodb_log_file_size` 在新版本已不建议使用。
- 固定大小、**循环写**：写满后回到头部覆盖，被覆盖的位置必须已经 checkpoint（对应的脏页已刷盘）。

### 3. 写入机制：buffer → 磁盘

redo 的写入分两层，这两层经常被混为一谈：

- **写 buffer（内存）**：每条 redo 记录顺序追加到 `redo log buffer`（`innodb_log_buffer_size`，默认 16MB）。这一步非常轻，只是内存拷贝。
- **刷盘（磁盘）**：把 buffer 里的内容 write 到文件、必要时 fsync。**这才是所谓"提交时刷盘"真正指的动作。**

刷盘不只由提交触发，一共有四个触发点：

1. **事务提交**：按 `innodb_flush_log_at_trx_commit` 决定 write / fsync 的强度。
2. **buffer 剩余空间不足 1/2**：直接 write 到文件（**只 write，不 fsync**），腾出空间让事务继续写，避免被日志阻塞。
3. **后台 master thread**：每秒做一次 write + fsync。
4. **checkpoint 推进 / 实例正常关闭**：把该落的部分落干净。

### 4. 刷盘策略（`innodb_flush_log_at_trx_commit`）

| 取值       | 提交时的动作              | 安全性                | 适用场景            |
| -------- | ------------------- | ------------------ | --------------- |
| **1**（默认） | write + fsync       | 提交返回即落盘，不丢         | 金融、订单、结算等不能丢账的业务 |
| **2**    | 只 write 到 OS page cache，不 fsync | MySQL 进程崩溃不丢，主机断电丢 1 秒内 | 一般业务，稳妥的折中      |
| **0**    | 提交时什么都不做，全靠每秒后台刷    | 进程崩溃也会丢            | 极高吞吐、允许少量丢失     |

> 注意 2 和 0 的差别：**2 是"写进了操作系统"，0 是"还在 MySQL 自己的内存里"**。所以 2 能挡住 MySQL 进程被 kill，挡不住断电。

### 5. 特点

- **顺序写**，性能高（顺序 IO 远快于随机 IO）。
- 只记录"页被改成了什么"，不记录"如何撤销"，因此可以重复重放，天然幂等（配合 LSN 判断）。
- 刷盘由 fsync 保证，但高并发下**组提交（group commit）** 会把多个事务的 fsync 合并成一次，实际的 fsync 次数远小于事务数。

## Undo Log

### 1. 作用

- **实现事务的原子性（Atomicity）**：回滚未提交的事务。
- **支撑 MVCC**：一致性读需要看到"事务开始那一刻的旧版本"，数据源就是 undo 版本链。

### 2. 存储位置

- 存储在 **undo 表空间**。MySQL 8.0 默认两个独立 undo 表空间：`undo_001`、`undo_002`（5.6 之前只能在共享表空间 `ibdata1` 里）。

### 3. 写入机制

- 记录的是**逻辑操作的反向操作**：INSERT 对应 DELETE，UPDATE 记录旧值（并把旧值串成版本链的 `roll_ptr`）。
- 属于**逻辑日志**，与 redo 的物理日志相对。
- 在事务执行过程中随每条 DML 生成，**提交后不立即删除**——快照读可能还要用它。由 **purge 线程**异步清理，判断依据是"没有比它更老的 Read View 还在引用"。

### 4. 特点

- **不直接用于崩溃恢复**（崩溃恢复靠 redo）。但 undo 页的修改本身也要写 redo，所以崩溃后 undo 也能被恢复出来。
- 是实现**可重复读（RR）** 隔离级别的关键：MVCC 的版本链就是 undo 链。
- 长事务会让 undo 无法 purge，导致 undo 表空间膨胀、版本链变长、快照读变慢——这是长事务最主要的危害。

## Bin Log

### 1. 作用

- **主从复制（Replication）**：主库把 binlog 发给从库，从库重放实现同步。
- **基于时间点的恢复（PITR）**：全量备份 + binlog 重放，恢复到任意时刻。
- 审计与数据变更追踪。

### 2. 存储位置

- 由 **MySQL Server 层**管理，与存储引擎无关；默认关闭，需配置 `log_bin` 开启。
- 文件名如 `mysql-bin.000001`、`mysql-bin.000002`……追加写、不覆盖，按 `max_binlog_size` 轮转。

### 3. 日志格式（`binlog_format`）

| 格式            | 记录内容        | 优点      | 缺点                     |
| ------------- | ----------- | ------- | ---------------------- |
| **STATEMENT** | SQL 语句原文    | 日志量小    | `NOW()`、`RAND()`、`LIMIT` 等可能导致主从不一致 |
| **ROW**（8.0 默认） | 每一行数据的变更前后值 | 精确、可审计  | 日志量大，批量更新尤甚            |
| **MIXED**     | 由 MySQL 自动选择 | 折中      | 行为不直观，排查困难             |

### 4. 写入机制：cache → 文件

binlog 的写入同样是两层，但和 redo 的节奏完全不同：

- **执行期间**：变更事件写入**线程私有的 `binlog cache`**（`binlog_cache_size`，默认 32KB），此时完全没有碰磁盘文件。
- **提交时**：把该事务在 cache 里的内容 write 到 binlog 文件，再按 `sync_binlog` 决定是否 fsync。
- **大事务的例外**：单事务的 binlog 超过 `binlog_cache_size` 后，会落到**临时文件**（磁盘）上，之后提交时再合并写入 binlog。所以"大事务在执行过程中就在写磁盘"是成立的，这也是大事务慢的原因之一。可以通过 `binlog_cache_disk_use` 观察这种情况发生了多少次。

### 5. 刷盘策略（`sync_binlog`）

| 取值       | 行为               | 风险                     |
| -------- | ---------------- | ---------------------- |
| **1**（8.0 默认） | 每次提交都 fsync     | 最安全，但每次提交一次 fsync      |
| **0**    | 交给操作系统决定何时刷      | 断电可能丢一段 binlog        |
| **N**    | 每累积 N 个事务 fsync 一次 | 宕机最多丢 N 个事务，兼顾性能       |

> 严格来说 `sync_binlog=1` 也不等于"零丢失"：`fsync` 之外还有磁盘自身写缓存的问题，但那是硬件层面的话题了。

### 6. 特点

- **追加写入（Append-only）**，不会覆盖已有内容。
- 过期自动清理：`binlog_expire_logs_seconds`（默认 2592000，即 30 天）。老的 `expire_logs_days` 已废弃。
- **不参与崩溃恢复**，但可用于 PITR。
- 事务提交前会给 binlog 加上 XID 事件，这个 XID 是两阶段提交中与 redo 对齐的凭据。

## 两阶段提交（2PC）

### 1. 流程

1. **Prepare 阶段**：InnoDB 把 redo 写入并标记为 `prepare`，同时记录事务 XID，按 `innodb_flush_log_at_trx_commit` 刷盘。
2. **写 Binlog**：Server 层把 binlog cache 写入 binlog 文件，按 `sync_binlog` 刷盘。
3. **Commit 阶段**：InnoDB 把 redo 中的事务标记为 `commit`。

### 2. 为什么第三步不需要刷盘

因为**判断事务是否提交的依据已经在 binlog 里了**。binlog 落盘之后，即使 commit 标记还没刷、机器就断电，重启后按下面的规则依然能得出正确结论：

| 崩溃时的状态                        | 恢复动作        | 结果     |
| ----------------------------- | ----------- | ------ |
| redo 为 prepare + binlog 完整（含该 XID） | 前滚重放        | 事务生效   |
| redo 为 prepare + binlog 不完整/不存在   | 回滚          | 事务不生效  |
| redo 已是 commit                 | 直接前滚        | 事务生效   |

所以第三步只是一个内存里的状态更新，随 checkpoint 慢慢刷下去即可——这正是 2PC 省下的那一次 fsync。

### 3. 顺序不能反

如果先写 binlog 再写 redo prepare，会出现"从库应用了、主库却回滚了"的错位；如果 redo 先 commit 再写 binlog，则会出现"主库提交了、binlog 没记、从库永远缺这条"。**redo prepare 在前、binlog 居中、redo commit 在后**，是唯一能让两份日志结论一致的顺序。

## 常见误区速查

1. **"redo 是提交时才写的"** ❌ —— 执行过程中就一直在写 buffer，提交只是触发了一次强刷。
2. **"binlog 是提交之后写的"** ❌ —— 是在提交**过程中**、redo prepare **之后**写的，属于 commit 的一部分，不是之后追加的动作。
3. **"redo 先写、binlog 后写"说得太粗** —— 完整顺序是 redo（prepare）→ binlog → redo（commit），有两次 redo 写入。
4. **"提交时只有一次 fsync"** ❌ —— 参数都为 1 时每个事务两次 fsync（redo 一次、binlog 一次），只是组提交会把并发事务合并。
5. **"undo 提交后就删了"** ❌ —— 要等 purge 判断没有更老的 Read View 引用它，才真正回收。
