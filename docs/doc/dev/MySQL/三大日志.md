> **一句话**：三道日志的写入时机之所以容易混，是因为它们被**三个不同的顺序关系**约束，而这三个关系常被压成一句话讲。
>
> 1. **日志内部**：一条日志先写内存 buffer，再写磁盘文件 —— 由 `innodb_flush_log_at_trx_commit`、`sync_binlog` 控制。
> 2. **日志与数据页**：redo 必须先于脏页落盘，即 **WAL**。
> 3. **redo 与 binlog**：redo prepare 先于 binlog，binlog 先于 redo commit，即 **2PC**。
>
> 把"写到哪一层"和"谁必须等谁"分开看，后文所有关于时机的描述就都有位置了。

## 一、三道日志的定位

| 特性     | Redo Log        | Undo Log      | Binlog                    |
| ------ | --------------- | ------------- | ------------------------- |
| 所属层级   | InnoDB 引擎层      | InnoDB 引擎层    | MySQL Server 层            |
| 解决什么问题 | 持久性、崩溃恢复        | 原子性、MVCC      | 主从复制、PITR、审计             |
| 日志类型   | 物理日志（页级）        | 逻辑日志（反向操作）    | 逻辑日志（ROW / STATEMENT）     |
| 文件形态   | 固定大小、循环写        | undo 表空间，由 purge 回收 | 追加写、按大小轮转                 |
| 默认开启   | 是（InnoDB）       | 是（InnoDB）     | 否（需配置 `log_bin`）          |

一句话记住分工：**redo 管"改了什么"，undo 管"怎么撤回去"，binlog 管"对外宣布发生了什么"。**

## 二、写入路径：写到内存还是写到磁盘

三道日志都**不是直接写文件的**，各自先落在一块私有的内存区，再由不同机制推到磁盘。这是第一个容易混的地方。

### 2.1 三道日志的写入位置

| 日志         | 执行期写在内存的哪里              | 提交时做什么                     | 落盘由谁控制                          |
| ---------- | ----------------------- | -------------------------- | ------------------------------- |
| **Redo**   | `redo log buffer`，默认 16MB | write + fsync，事务状态从 prepare 切成 commit | `innodb_flush_log_at_trx_commit` |
| **Undo**   | undo buffer（本身也受 redo 保护） | 不删、不动，留着给 MVCC 和回滚         | 无，由 purge 线程异步回收                |
| **Binlog** | 线程私有 `binlog cache`，默认 32KB | 从 cache write 到 binlog 文件，再按需 fsync | `sync_binlog`                     |

### 2.2 一次事务的完整时序

```text
事务执行中
  ├─ 修改 Buffer Pool 中的数据页（页变成脏页）
  ├─ 写 Undo Log（这条 undo 记录本身也受 Redo 保护）
  └─ 写 Redo Log Buffer
                │
         用户执行 COMMIT
                │
  ① InnoDB Prepare：Redo Log 刷盘，事务状态置为 prepare        ← fsync
  ② Server 层：binlog cache → binlog 文件，按 sync_binlog 决定是否 fsync  ← 可能 fsync
  ③ InnoDB Commit：Redo Log 写入 commit 标记（不需要立即刷盘）      ← 无 fsync
```

注意：一次提交里真正的刷盘点只有 ① 和 ② 两处。第三步只是内存里的状态更新，这正是 2PC 省下来的那一次 fsync（原因见第四章）。

### 2.3 为什么一定要分两层

如果每条日志都直接 fsync 到磁盘，一次事务可能要几百次随机写。有了 buffer，多条记录可以攒成一次顺序写 —— 这是日志敢于"记录每一页修改"的前提。

也正因为有缓存层，才存在"提交刷盘"与"后台刷盘"两套节奏。**Redo 有四个刷盘触发点：**

1. **事务提交**：按 `innodb_flush_log_at_trx_commit` 决定 write / fsync 的强度。
2. **buffer 剩余空间不足 1/2**：直接 write 到文件（**只 write，不 fsync**），腾出空间让事务继续写，避免被日志阻塞。
3. **后台 master thread**：每秒做一次 write + fsync。
4. **checkpoint 推进 / 实例正常关闭**：把该落的部分落干净。

**Binlog 则有一个例外：** 单事务的 binlog 超过 `binlog_cache_size` 后，会落到**临时文件**上，提交时再合并进 binlog。所以"大事务在执行过程中就在写磁盘"成立，这也是大事务慢的原因之一。用 `binlog_cache_disk_use` 可以统计这种情况发生了多少次。

## 三、顺序约束（一）：redo 为什么不能等提交（WAL）

### 3.1 两道日志的参照物不同

差别不在写入速度，而在**各自要对谁负责**：

| 日志         | 它要对谁负责     | 必须守住的关系                             |
| ---------- | ---------- | ----------------------------------- |
| **redo**   | 数据页的磁盘状态   | 任何已经写进磁盘数据页的修改，都要有对应的 redo 记录在磁盘上   |
| **binlog** | 事务的对外可见性   | 一个事务要么完整出现在 binlog 里，要么完全不出现        |

redo 的参照物是"页"，而页什么时候被刷走不可控；binlog 的参照物是"提交"，只跟事务边界有关。这就是一个必须贴身跟着、一个可以攒着的原因。

### 3.2 核心不变式

> **磁盘上的数据页，永远不能比 redo 文件更"新"。**

换句话说，redo 的落盘进度不能落后于脏页的刷盘进度。

注意措辞 —— **不是"每次改页都 fsync"，而是"每条改页都产生 redo，且 redo 的持久化不能掉队"**。之所以看起来像"每改一页就跟一笔"，是因为脏页何时被刷走无法预测：后台线程在刷、checkpoint 在刷、LRU 淘汰也在刷，所以 redo 只能持续往前推。

这是靠**阻塞**实现的，不是靠运气：刷任一脏页之前，都要先把 redo 落盘推进到覆盖该页的 LSN，拿到 fsync 确认才放行写页。所以"页已落盘、而 redo 还在内存"这个状态在设计上根本发不出来。

### 3.3 违反后会怎样

崩溃时，buffer pool 里哪些页脏、脏到什么程度，全部随内存一起消失，恢复程序手上只剩磁盘上的字节。它无从判断某一页现在是哪一种状态：

```text
① 完好的旧版本
② 完好的新版本
③ 写到一半的混合体（撕裂页 / torn page）
```

而一次页写入**不是原子操作**：16KB 的页要拆成多个 4KB 块陆续落盘，中途断电就会留下第 ③ 种 —— 前半截是新数据、后半截还是旧数据，这个页在逻辑上已经是坏的。redo 的唯一作用，就是把这份"不确定"重新变成"确定"：

```text
有 redo：不管这页当前是①②③哪种，按 redo 从头重放一遍，必然收敛到"新"；
        再由 undo 决定这个事务该保留还是该撤回。
无 redo：这页就是一团来历不明的字节，既无法证明它合法，也没有依据把它改回去。
```

所以"数据页彻底坏了"的准确含义不是"丢了一次修改"，而是**失去了判断这一页是什么的能力**。

### 3.4 那 binlog 为什么可以攒

因为它的消费者不是崩溃恢复里的页，而是**从库重放**和**按时间点恢复（PITR）**。它们只关心"这个事务的变更是否完整、顺序是否正确"，不关心某个页何时落盘，也不参与 undo/回滚。

它唯一受方向性约束的地方在下一章 —— 但那里的参照物是"提交是否可见"，不是"页有没有刷脏"，两条约束的锚点不在同一处。

> 顺带澄清：`doublewrite buffer` 会先把页写一份副本再写正式位置，用于**降低**撕裂页的概率。但它只是一层保险，不承担"判断这页到底是什么"的职责，裁决者仍然是 redo，不能拿它替代 WAL。

## 四、顺序约束（二）：两阶段提交

### 4.1 三步流程

1. **Prepare**：InnoDB 把 redo 写入并标记为 `prepare`，同时记录事务 XID，按 `innodb_flush_log_at_trx_commit` 刷盘。
2. **写 Binlog**：Server 层把 binlog cache 写入 binlog 文件，按 `sync_binlog` 刷盘，并给事务加上 XID 事件。
3. **Commit**：InnoDB 把 redo 中的事务标记为 `commit`。

### 4.2 为什么第三步不用刷盘

因为**判断事务是否提交的依据已经在 binlog 里了**。binlog 落盘之后，即使 commit 标记还没刷就断电，重启后按下面的规则依然能得出正确结论：

| 崩溃时的状态                          | 恢复动作 | 结果    |
| ------------------------------- | ---- | ----- |
| redo 为 prepare + binlog 完整（含该 XID） | 前滚重放 | 事务生效  |
| redo 为 prepare + binlog 不完整/不存在    | 回滚   | 事务不生效 |
| redo 已是 commit                   | 直接前滚 | 事务生效  |

### 4.3 顺序不能反

- 先写 binlog 再写 redo prepare → "从库应用了、主库却回滚了"。
- redo 先 commit 再写 binlog → "主库提交了、binlog 没记、从库永远缺这条"。

**redo prepare 在前、binlog 居中、redo commit 在后**，是唯一能让两份日志结论一致的顺序。

## 五、Redo Log

### 5.1 作用

- 保证事务的**持久性（Durability）**。
- 数据库异常宕机时用于**崩溃恢复（Crash Recovery）**，确保已提交事务的修改不丢失。

### 5.2 存储位置

- 物理文件，位于数据目录下。
- **8.0.30 之前**：`ib_logfile0`、`ib_logfile1`，文件数与大小由 `innodb_log_files_in_group`、`innodb_log_file_size` 控制。
- **8.0.30 及之后**：改为 `#innodb_redo/` 目录下的 32 个 `#ib_redo*` 文件，总容量由 `innodb_redo_log_capacity` 控制（默认 100MB）；`innodb_log_file_size` 已不建议使用。
- **固定大小、循环写**：写满后回到头部覆盖。可被覆盖的前提是该位置之前的修改已经 checkpoint（对应脏页已刷盘）—— 这保证日志不会"早退"。

### 5.3 刷盘策略（`innodb_flush_log_at_trx_commit`）

| 取值       | 提交时的动作                          | 安全性                | 适用场景            |
| -------- | ------------------------------- | ------------------ | --------------- |
| **1**（默认） | write + fsync                   | 提交返回即落盘，不丢         | 金融、订单、结算等不能丢账的业务 |
| **2**    | 只 write 到 OS page cache，不 fsync | MySQL 进程崩溃不丢，主机断电丢 1 秒内 | 一般业务，稳妥的折中      |
| **0**    | 提交时什么都不做，全靠每秒后台刷                | 进程崩溃也会丢            | 极高吞吐、允许少量丢失     |

> 注意 2 和 0 的差别：**2 是"写进了操作系统"，0 是"还在 MySQL 自己的内存里"**。所以 2 能挡住 MySQL 进程被 kill，挡不住断电。

### 5.4 特点

- **顺序写**，性能高（顺序 IO 远快于随机 IO）。
- 只记录"页被改成了什么"，不记录"如何撤销"，因此可以重复重放，天然幂等（配合 LSN 判断）。
- 高并发下**组提交（group commit）** 会把多个事务的 fsync 合并成一次，实际 fsync 次数远小于事务数。

## 六、Undo Log

### 6.1 作用

- 实现事务的**原子性（Atomicity）**：回滚未提交的事务。
- 支撑 **MVCC**：一致性读需要看到"事务开始那一刻的旧版本"，数据源就是 undo 版本链。

### 6.2 存储位置

- 存储在 **undo 表空间**。MySQL 8.0 默认两个独立 undo 表空间：`undo_001`、`undo_002`（5.6 之前只能在共享表空间 `ibdata1` 里）。

### 6.3 记录内容与回收

- 记录的是**逻辑操作的反向操作**：INSERT 对应 DELETE，UPDATE 记录旧值（并把旧值串成版本链的 `roll_ptr`）。
- 随每条 DML 生成，**提交后不立即删除** —— 快照读可能还要用它。
- 由 **purge 线程**异步清理，判断依据是"没有比它更老的 Read View 还在引用"。

### 6.4 特点

- **不直接用于崩溃恢复**（崩溃恢复靠 redo）。但 undo 页的修改本身也要写 redo，所以崩溃后 undo 也能被恢复出来。
- 是实现**可重复读（RR）** 的关键：MVCC 的版本链就是 undo 链。
- 长事务会让 undo 无法 purge，导致 undo 表空间膨胀、版本链变长、快照读变慢 —— 这是长事务最主要的危害。

## 七、Bin Log

### 7.1 作用

- **主从复制（Replication）**：主库把 binlog 发给从库，从库重放实现同步。
- **基于时间点的恢复（PITR）**：全量备份 + binlog 重放，恢复到任意时刻。
- 审计与数据变更追踪。

### 7.2 存储位置

- 由 **MySQL Server 层**管理，与存储引擎无关；默认关闭，需配置 `log_bin` 开启。
- 文件名如 `mysql-bin.000001`、`mysql-bin.000002`……追加写、不覆盖，按 `max_binlog_size` 轮转。

### 7.3 日志格式（`binlog_format`）

| 格式                | 记录内容        | 优点     | 缺点                                 |
| ----------------- | ----------- | ------ | ---------------------------------- |
| **STATEMENT**     | SQL 语句原文    | 日志量小   | `NOW()`、`RAND()`、`LIMIT` 等可能导致主从不一致 |
| **ROW**（8.0 默认）   | 每一行数据的变更前后值 | 精确、可审计 | 日志量大，批量更新尤甚                        |
| **MIXED**         | 由 MySQL 自动选择 | 折中     | 行为不直观，排查困难                         |

### 7.4 刷盘策略（`sync_binlog`）

| 取值       | 行为               | 风险                |
| -------- | ---------------- | ----------------- |
| **1**（8.0 默认） | 每次提交都 fsync     | 最安全，但每次提交一次 fsync |
| **0**    | 交给操作系统决定何时刷      | 断电可能丢一段 binlog    |
| **N**    | 每累积 N 个事务 fsync 一次 | 宕机最多丢 N 个事务，兼顾性能  |

> 严格来说 `sync_binlog=1` 也不等于"零丢失"：`fsync` 之外还有磁盘自身写缓存的问题，那属于硬件层面的话题。

### 7.5 特点

- **追加写入（Append-only）**，不会覆盖已有内容。
- 过期自动清理：`binlog_expire_logs_seconds`（默认 2592000，即 30 天）。老的 `expire_logs_days` 已废弃。
- **不参与崩溃恢复**，但可用于 PITR。
- 事务提交前会带上 XID 事件，这是 2PC 中与 redo 对齐的凭据。

## 八、常见误区速查

1. **"redo 是提交时才写的"** ❌ —— 执行过程中就一直在写 buffer，提交只是触发了一次强刷。
2. **"binlog 是提交之后写的"** ❌ —— 是在提交**过程中**、redo prepare **之后**写的，属于 commit 的一部分。
3. **"redo 先写、binlog 后写"说得太粗** —— 完整顺序是 redo（prepare）→ binlog → redo（commit），有两次 redo 写入。
4. **"提交时只有一次 fsync"** ❌ —— 参数都为 1 时每事务两次 fsync（redo 一次、binlog 一次），组提交会把并发事务合并。
5. **"undo 提交后就删了"** ❌ —— 要等 purge 判断没有更老的 Read View 引用它，才真正回收。
6. **"redo 必须每次改页都 fsync"** ❌ —— 正确说法是"每条改页都产生 redo，且落盘不能落后于脏页刷盘"，频率由刷脏节奏倒逼。
7. **"崩在刷脏中途只是丢了一次修改"** ❌ —— 更严重的是数据页变成撕裂页，恢复程序失去判断它属于哪个版本的能力。
8. **"写入时机可以一句话说清"** ❌ —— 实际是三层独立约束：日志的内存/磁盘、日志与数据页、redo 与 binlog。混着讲必乱。
