

## 事务的四大特性（ACID）

**一句话**：A、I、D 是手段，C 是目的。原子性管“全做或全不做”，隔离性管“并发不串味”，持久性管“提交了就不丢”，三者合起来才叫“数据一致”。

<AcidOverview />

| 特性 | 一句话定义 | InnoDB 的落地手段 | 不保证会怎样 |
| --- | --- | --- | --- |
| **A · 原子性**<br>Atomicity | 事务内的操作是不可分割的整体 | **undo log** 记录反向操作，回滚时按版本链逆序补偿 | 转账扣了钱、没加到对方账上 |
| **I · 隔离性**<br>Isolation | 并发事务互不干扰，看不到对方未提交的中间态 | 写走**行锁 + 间隙锁**，读走 **MVCC 快照读** | 脏读、不可重复读、幻读 |
| **D · 持久性**<br>Durability | 只要 COMMIT 返回成功，宕机也不丢 | **redo log** 的 WAL，配合 `innodb_flush_log_at_trx_commit=1` 每次提交刷盘 | 提交后断电，数据凭空回退 |
| **C · 一致性**<br>Consistency | 事务前后数据都满足业务与库的约束 | **没有独立机制**：A + I + D 的结果，再加约束校验（唯一索引、CHECK、外键） | 余额被扣成负数、总分账不平 |

### 为什么“一致性”是结果而不是手段

其他三个特性都能指出具体组件（undo log / 锁 + MVCC / redo log），只有一致性指不出来，因为它约束的是**业务语义**，不是某段代码：

- 数据库只能保证**规则内**的部分：唯一索引挡重复、CHECK 挡越界、外键挡孤儿行。
- **规则外**的部分（“A 账户扣 100，B 账户必须加 100”“库存不能卖超”）只能靠应用层：要么业务代码写对，要么用触发器/约束把规则搬进库里。
- 所以 A、I、D 任一失效，一致性立刻崩；但三者都满足，也**不等于**业务一致 —— 代码算错金额，数据库会老老实实存下这笔错账。

### 三个容易答错的点

1. **undo log 不只是拿来回滚的**。它同时是 MVCC 读旧版本的数据源：快照读要找到“这个事务开始时的值”，走的就是 undo 版本链。所以“undo log 只服务原子性”是错的。
2. **redo 是物理日志，undo 是逻辑日志**，容易记反。redo 记“某页某偏移改成了什么”，因此能重复重放；undo 记“这行原来是什么值”，只能按顺序逆向补偿。对比见 [三大日志](/doc/dev/MySQL/三大日志)。
3. **binlog 不参与崩溃恢复**。宕机恢复靠 redo log；binlog 服务的是主从复制和按时间点恢复。两者要靠**两阶段提交**（redo prepare → 写 binlog → redo commit）对齐，否则会出现“主库有、从库没有”或“从库多一条”的错位。

## 事务问题

| 问题    | 表现               | 如何解决                              |
| ----- | ---------------- | --------------------------------- |
| 脏读    | 事务A能读到事务B未提交的修改。 | 读已提交通过每执行一次`select`生成一个读视图。       |
| 不可重复读 | 事务A能读到事务B已提交的修改。 | 可重复读通过第一次`select`生成唯一读视图，后续复用此视图。 |
| 幻读    | 事务A能读到事务B已提交的新增。 | 依赖读视图 + 临键锁实现。                    |

[^读视图]: MVCC组件



## 事务隔离级别

### 读未提交（READ UNCOMMITTED）

**特点**：
- 允许事务读取其他事务未提交的数据
- **问题**：脏读、不可重复读、幻读都可能发生

**适用场景**：极少使用，仅用于对数据一致性要求极低的场景

### 读已提交（Read Committed）

**特点**：
- 事务只能读取其他事务已提交的数据
- **解决脏读**：每次 `SELECT` 生成一个新的读视图
- **问题**：不可重复读、幻读仍可能发生

**适用场景**：Oracle 默认隔离级别，适用于大多数业务场景

### 可重复读（Repeatable Read）

**特点**：
- MySQL InnoDB 默认隔离级别
- **解决不可重复读**：事务中第一次 `SELECT` 生成唯一读视图，后续复用
- **解决幻读**：配合间隙锁（Gap Lock）实现

**读视图机制**：
- 事务开始时创建 Read View
- 后续查询复用该视图，保证同一事务内读取的数据一致

### 串行化（SERIALIZABLE）

**特点**：
- 最高隔离级别，完全串行执行事务
- 每个事务依次执行，不存在并发
- **解决所有问题**：脏读、不可重复读、幻读

**适用场景**：
- 数据一致性要求极高的场景
- 并发量极低的场景

### 隔离级别对比

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 性能 |
|---------|------|-----------|------|------|
| READ UNCOMMITTED | ✅ | ✅ | ✅ | 最高 |
| READ COMMITTED | ❌ | ✅ | ✅ | 高 |
| REPEATABLE READ | ❌ | ❌ | ❌（InnoDB） | 中 |
| SERIALIZABLE | ❌ | ❌ | ❌ | 最低 |

### InnoDB 的 MVCC + 锁机制

**快照读（普通 SELECT）**：
- 使用 MVCC，不加锁，读取历史版本
- 适用于读多写少的场景

**当前读（加锁读）**：
- `SELECT ... FOR UPDATE`：加排他锁
- `SELECT ... FOR SHARE`：加共享锁
- `UPDATE` / `DELETE` / `INSERT`：自动加锁
- 适用于需要数据一致性的场景
