

## 事务问题

| 问题    | 表现               | 如何解决                              |
| ----- | ---------------- | --------------------------------- |
| 脏读    | 事务A能读到事务B未提交的修改。 | 读已提交通过每执行一次`select`生成一个读视图。       |
| 不可重复读 | 事务A能读到事务B已提交的修改。 | 可重复读通过第一次`select`生成唯一读视图，后续复用此视图。 |
| 幻读    | 事务A能读到事务B已提交的新增。 | 依赖读视图 + 临键锁实现。                    |

[^读视图]: MVCC组件



## 事务隔离级别

### 读未提交（READ UNCOMMITTED）

**特点**：
- 允许事务读取其他事务未提交的数据
- **问题**：脏读、不可重复读、幻读都可能发生

**适用场景**：极少使用，仅用于对数据一致性要求极低的场景

### 读已提交（Read Committed）

**特点**：
- 事务只能读取其他事务已提交的数据
- **解决脏读**：每次 `SELECT` 生成一个新的读视图
- **问题**：不可重复读、幻读仍可能发生

**适用场景**：Oracle 默认隔离级别，适用于大多数业务场景

### 可重复读（Repeatable Read）

**特点**：
- MySQL InnoDB 默认隔离级别
- **解决不可重复读**：事务中第一次 `SELECT` 生成唯一读视图，后续复用
- **解决幻读**：配合间隙锁（Gap Lock）实现

**读视图机制**：
- 事务开始时创建 Read View
- 后续查询复用该视图，保证同一事务内读取的数据一致

### 串行化（SERIALIZABLE）

**特点**：
- 最高隔离级别，完全串行执行事务
- 每个事务依次执行，不存在并发
- **解决所有问题**：脏读、不可重复读、幻读

**适用场景**：
- 数据一致性要求极高的场景
- 并发量极低的场景

### 隔离级别对比

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 性能 |
|---------|------|-----------|------|------|
| READ UNCOMMITTED | ✅ | ✅ | ✅ | 最高 |
| READ COMMITTED | ❌ | ✅ | ✅ | 高 |
| REPEATABLE READ | ❌ | ❌ | ❌（InnoDB） | 中 |
| SERIALIZABLE | ❌ | ❌ | ❌ | 最低 |

### InnoDB 的 MVCC + 锁机制

**快照读（普通 SELECT）**：
- 使用 MVCC，不加锁，读取历史版本
- 适用于读多写少的场景

**当前读（加锁读）**：
- `SELECT ... FOR UPDATE`：加排他锁
- `SELECT ... FOR SHARE`：加共享锁
- `UPDATE` / `DELETE` / `INSERT`：自动加锁
- 适用于需要数据一致性的场景
