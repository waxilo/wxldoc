## 聚簇索引

在innodb存储引擎下，每个表有且只有一个聚簇索引，通常为主键或隐藏主键。

## B+树

### 为什么选择 B+ 树？

| 数据结构     | 是否适合磁盘存储 | 范围查询      | 插入/删除效率  | 说明            |
| -------- | -------- | --------- | -------- | ------------- |
| 二叉搜索树    | ❌        | ✅         | ❌（退化为链表） | 高度不可控         |
| 平衡树（AVL） | ❌        | ✅         | ⚠️（频繁旋转） | 仍太高，I/O 多     |
| B 树      | ✅        | ⚠️（需中序遍历） | ✅        | 数据存在内部节点      |
| B+ 树     | ✅✅       | ✅✅        | ✅✅       | 数据只在叶子，叶子链表连接 |
✅ **B+ 树优势**：

- **高度低**：一个节点可存多个 key，减少磁盘 I/O（通常 3～4 层可存千万级数据）
- **范围查询高效**：叶子节点用双向链表连接，顺序扫描快
- **全表扫描友好**：只需遍历叶子链表
- **稳定性好**：插入/删除不会频繁调整树结构

## 索引失效场景

| 场景                       | 示例                                                                                               |
| ------------------------ | ------------------------------------------------------------------------------------------------ |
| 索引列使用函数                  | SELECT * FROM users WHERE YEAR(create_time) = 2025;                                              |
| 索引列参与运算                  | SELECT * FROM orders WHERE amount > 100 / 1.1;                                                   |
| 类型隐式转换                   | -- 假设 phone 是 VARCHAR 类型<br>SELECT * FROM users WHERE phone = 13800138000;                       |
| 使用 `!=` 或 `<>`（非等值查询）    | -- 可能失效（除非走覆盖索引） <br>SELECT * FROM users WHERE status != 1;                                      |
| 使用 `NOT IN`、`NOT EXISTS` | SELECT * FROM users WHERE id NOT IN (SELECT user_id FROM orders);                                |
| `LIKE` 以通配符开头（前导模糊）      | SELECT * FROM users WHERE name LIKE '%john%';                                                    |
| 组合索引非最左匹配                | -- 假设（a,b,c）索引<br>SELECT * FROM users WHERE  b = 2 AND c = 3；                                    |
| `OR` 条件中部分列无索引           | -- 假设只有 idx_name(name) 索引 ，age 无索引<br>SELECT * FROM users WHERE name = 'Alice' OR age = 25;      |
| 数据倾斜                     | -- 比如 gender 字段：99% 是 'M'，1% 是 'F'，即使有索引，查 'M' 时可能走全表<br>SELECT * FROM users WHERE gender = 'M'; |
| `SELECT *`回标成本高，放弃使用索引   | SELECT * from users                                                                              |

## 索引优化建议

### 创建索引原则

| 原则 | 说明 |
|------|------|
| 选择区分度高的列 | 区分度越高，索引效果越好（可用 `COUNT(DISTINCT col)/COUNT(*)` 评估） |
| 索引不是越多越好 | 索引占用额外空间，影响写操作性能（INSERT/UPDATE/DELETE） |
| 利用最左前缀原则 | 复合索引从左到右使用，避免索引失效 |
| 覆盖索引优先 | 让索引包含查询所需全部字段，减少回表 |

### 高频面试题

**Q1: 聚簇索引 vs 非聚簇索引**

| 特性 | 聚簇索引 | 非聚簇索引 |
|------|----------|------------|
| 数据存储 | 叶节点存储完整数据行 | 叶节点存储索引值和主键 |
| 查询方式 | 主键查询直接定位数据 | 先查索引，再回表查数据 |
| 插入性能 | 主键自增时插入快 | 无影响 |
| 空间占用 | 一个表一个 | 可以有多个 |
| 适用场景 | 主键查询、范围查询 | 高频查询字段 |

**Q2: 主键索引 vs 唯一索引**

| 特性 | 主键索引 | 唯一索引 |
|------|----------|----------|
| 约束 | 唯一且非空 | 唯一但可为空 |
| 数量 | 一个表只能一个 | 可以有多个 |
| 自动创建 | 表创建时自动 | 手动创建 |
| 索引结构 | 聚簇索引 | 非聚簇索引 |

**Q3: 复合索引的最左前缀原则**

假设有复合索引 `(name, age, gender)`：

```sql
-- ✅ 走索引（使用最左前缀）
SELECT * FROM users WHERE name = 'Alice';
SELECT * FROM users WHERE name = 'Alice' AND age = 25;

-- ❌ 不走索引（跳过最左列）
SELECT * FROM users WHERE age = 25;
SELECT * FROM users WHERE gender = 'F';
```

**Q4: 索引下推（Index Condition Pushdown, ICP）**

**作用**：在复合索引中，在索引遍历过程中就过滤数据，减少回表次数

**条件**：
- 适用于 `WHERE` 条件中包含索引列
- 用于 `range`、`ref`、`eq_ref`、`ref_or_null` 访问类型

**示例**：
```sql
-- 假设有索引 (name, age)
SELECT * FROM users WHERE name LIKE 'A%' AND age = 25;

-- 无 ICP：先根据 name 找到所有匹配的行，再回表检查 age
-- 有 ICP：在索引遍历时直接过滤 age = 25，减少回表次数
```

**Q5: 索引失效如何排查**

1. 使用 `EXPLAIN` 查看执行计划
2. 检查 `type` 列：ALL = 全表扫描
3. 检查 `key` 列：是否使用了索引
4. 检查 `Extra` 列：是否有 `Using filesort`、`Using temporary`、`Using index condition`

**Q6: 为什么 MongoDB 选 B 树而 MySQL 选 B+ 树**

| 对比 | MongoDB（B 树） | MySQL（B+ 树） |
|------|------------------|----------------|
| 数据存储 | 每个节点都存储数据 | 只有叶子节点存储数据 |
| 查询复杂度 | 最好 O(1)，最坏 O(log n) | 稳定 O(log n) |
| 范围查询 | 需要遍历所有节点 | 叶子节点链表连接，顺序遍历快 |
| 磁盘 I/O | 不稳定，可能多次 I/O | 稳定，可预估 I/O 次数 |

**Q7: 一条 SQL 是如何执行的**

```sql
SELECT * FROM users WHERE id = 1;
```

**执行流程**：
1. **连接器**：验证用户身份，建立连接
2. **查询缓存**：8.0 已移除（命中率低）
3. **分析器**：词法分析、语法分析
4. **优化器**：生成执行计划，选择索引
5. **执行器**：调用存储引擎接口执行
6. **存储引擎**：InnoDB 从磁盘读取数据页到内存

**Q8: count(*) vs count(1) vs count(字段)**

| 方式 | 说明 | 性能 |
|------|------|------|
| count(*) | 统计所有行数，包含 NULL | ✅ 最优 |
| count(1) | 统计所有行数，忽略 NULL | 略逊 |
| count(字段) | 统计非 NULL 行数 | 最差 |

**InnoDB 优化**：count(*) 和 count(1) 实际上没有区别，InnoDB 会选择最小的索引来扫描
