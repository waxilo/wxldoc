## 聚簇索引

**一句话**：聚簇索引（Clustered Index）就是「索引即数据」——B+ 树的叶子节点存放的不是指针，而是**完整的数据行**。索引和数据聚在同一棵树上，所以叫「聚簇」。

### 本质：一棵树既当索引又当数据

| 位置 | 存放内容 |
| --- | --- |
| 非叶子节点 | 主键值 + 子页指针（只做导航，不含数据） |
| 叶子节点 | 主键值 + **完整数据行**（所有列） |
| 叶子之间 | 按主键升序、双向链表串联 |

由此可以推出两条结论：

- **按主键查询只需一次 B+ 树查找**，走到叶子就是拿到了整行，不存在「再去别处取数据」这一步
- **数据的物理存储顺序 = 聚簇索引顺序 = 主键顺序**，所以 InnoDB 里「主键有序」等于「全表按主键有序落盘」

### 一个表只能有一个聚簇索引

数据行在磁盘上只能有一种物理排列方式，所以聚簇索引天然唯一。InnoDB 的选择顺序：

| 优先级 | 条件 | 聚簇索引 |
| --- | --- | --- |
| 1 | 显式定义了 `PRIMARY KEY` | 主键 |
| 2 | 无主键，但有 `NOT NULL` 的唯一索引 | 第一个满足条件的唯一索引 |
| 3 | 以上都没有 | 隐藏列 `DB_ROW_ID`（6 字节，全局自增） |

> ⚠️ 第 3 种情况对用户完全不可见，你也无法在 `WHERE` 里使用它 —— 无主键表等于把数据的组织权交给了 MySQL，所以规范上要求必须建自增主键。

### 二级索引与回表

除聚簇索引外，其他索引统统叫**二级索引**（辅助索引 / 非聚簇索引）：

| 对比 | 聚簇索引（主键） | 二级索引（普通 / 唯一） |
| --- | --- | --- |
| 数量 | 一个表一个 | 可以有多个 |
| 叶子节点内容 | 完整数据行 | **索引列值 + 主键值** |
| 一次查找能否拿到整行 | 能 | 不能，需要回表 |
| 排序依据 | 主键 | 索引列 |
| 是否需要独立空间 | 就是数据本身 | 额外占用空间 |

二级索引查到主键值之后，再拿主键去聚簇索引查一次取整行，这一步叫**回表**，代价是**多一次 B+ 树查找 + 多次随机 I/O**。

```sql
-- id 是主键（聚簇索引），name 上有二级索引 idx_name
SELECT * FROM users WHERE id = 1;         -- 1 次树查找，直接拿到整行
SELECT * FROM users WHERE name = 'Alice'; -- 2 次：idx_name 找到主键 → 回表取整行
```

**避免回表 = 覆盖索引**：查询需要的列全部包含在二级索引中，就不用回表，`EXPLAIN` 的 `Extra` 会显示 `Using index`。

```sql
-- 索引 idx_name_age (name, age)
SELECT name, age FROM users WHERE name = 'Alice';        -- Using index，不回表
SELECT name, age, email FROM users WHERE name = 'Alice'; -- 需要 email，必须回表
```

> 二级索引叶子为什么存主键而不是行地址？因为行地址会随页分裂、数据更新而移动，存主键就不用维护所有二级索引；代价就是多一次回表。

### 主键该怎么选

主键会被**每一个二级索引各存一份**，同时决定数据的物理顺序，所以选型极重要：

| 原则 | 原因 |
| --- | --- |
| 自增（`AUTO_INCREMENT`） | 插入永远追加在最后一页，不触发页分裂 |
| 尽量短（`BIGINT` 而非 `CHAR(32)`） | 主键长度会被放大到所有二级索引上 |
| 不用业务字段（手机号、身份证） | 业务值可变，主键一改就是整表重建 + 所有二级索引重建 |
| 不用随机值（UUID、无序 ID） | 随机插入 → 页分裂 → 碎片 → 写放大 |

**UUID 主键的真实代价**：新行的插入位置随机散布在已有页中间，目标页满了就要**页分裂**（一页拆成两页，各约 50% 满），磁盘上数据不再连续，范围查询和全表扫描都变慢。自增主键只在最后一页追加，页利用率接近 100%，满了直接开新页。

### 页分裂与页合并

| 操作 | 触发条件 | 结果 |
| --- | --- | --- |
| 页分裂 | 向已满的数据页（16KB）的中间位置插入 | 拆成两页，各约 50%，链表插入新页 |
| 页合并 | 相邻页利用率都低于阈值（约 50%） | 合并成一页，释放空间 |

页分裂是**写性能**问题，不是正确性问题，但它把顺序写变成了随机写 —— 这才是「UUID 主键慢」的根因。

### 和 MyISAM 的区别（非聚簇索引）

| 对比 | InnoDB（聚簇） | MyISAM（非聚簇） |
| --- | --- | --- |
| 索引与数据 | 同一棵 B+ 树，都在 `.ibd` | 索引 `.MYI`、数据 `.MYD` 分离 |
| 叶子节点存什么 | 完整数据行 | 行地址（offset） |
| 主键索引与二级索引 | 结构不同 | 结构完全一样 |
| 二级索引查询 | 回表查聚簇索引 | 按地址直接定位，不需要「主键」这一跳 |

### 高频追问

| 问题 | 回答要点 |
| --- | --- |
| 主键查询为什么快？ | 一次 B+ 树查找直达叶子，叶子就是数据，没有回表 |
| 一张表能有几个聚簇索引？ | 一个，数据只能有一种物理顺序 |
| 联合主键还有聚簇索引吗？ | 有，聚簇索引由联合主键构成，叶子按联合主键整体排序 |
| 没有主键会怎样？ | 退化到唯一索引 / 隐藏 `DB_ROW_ID`，不可控，不推荐 |
| 主键查询一定比二级索引快吗？ | 不一定。二级索引若已覆盖所需列就不回表，索引更小、层数更少，可能更快 |
| 二级索引能避免回表吗？ | 能，覆盖索引即可，`Extra` 出现 `Using index` |

## B+树

### 为什么选择 B+ 树？

| 数据结构     | 是否适合磁盘存储 | 范围查询      | 插入/删除效率  | 说明            |
| -------- | -------- | --------- | -------- | ------------- |
| 二叉搜索树    | ❌        | ✅         | ❌（退化为链表） | 高度不可控         |
| 平衡树（AVL） | ❌        | ✅         | ⚠️（频繁旋转） | 仍太高，I/O 多     |
| B 树      | ✅        | ⚠️（需中序遍历） | ✅        | 数据存在内部节点      |
| B+ 树     | ✅✅       | ✅✅        | ✅✅       | 数据只在叶子，叶子链表连接 |

✅ **B+ 树优势**：

- **高度低**：一个节点可存多个 key，减少磁盘 I/O（通常 3～4 层可存千万级数据）
- **范围查询高效**：叶子节点用双向链表连接，顺序扫描快
- **全表扫描友好**：只需遍历叶子链表
- **稳定性好**：插入/删除不会频繁调整树结构

## 索引失效场景

| 场景                       | 示例                                                                                               |
| ------------------------ | ------------------------------------------------------------------------------------------------ |
| 索引列使用函数                  | SELECT * FROM users WHERE YEAR(create_time) = 2025;                                              |
| 索引列参与运算                  | SELECT * FROM orders WHERE amount > 100 / 1.1;                                                   |
| 类型隐式转换                   | -- 假设 phone 是 VARCHAR 类型<br>SELECT * FROM users WHERE phone = 13800138000;                       |
| 使用 `!=` 或 `<>`（非等值查询）    | -- 可能失效（除非走覆盖索引） <br>SELECT * FROM users WHERE status != 1;                                      |
| 使用 `NOT IN`、`NOT EXISTS` | SELECT * FROM users WHERE id NOT IN (SELECT user_id FROM orders);                                |
| `LIKE` 以通配符开头（前导模糊）      | SELECT * FROM users WHERE name LIKE '%john%';                                                    |
| 组合索引非最左匹配                | -- 假设（a,b,c）索引<br>SELECT * FROM users WHERE  b = 2 AND c = 3；                                    |
| `OR` 条件中部分列无索引           | -- 假设只有 idx_name(name) 索引 ，age 无索引<br>SELECT * FROM users WHERE name = 'Alice' OR age = 25;      |
| 数据倾斜                     | -- 比如 gender 字段：99% 是 'M'，1% 是 'F'，即使有索引，查 'M' 时可能走全表<br>SELECT * FROM users WHERE gender = 'M'; |
| `SELECT *`回标成本高，放弃使用索引   | SELECT * from users                                                                              |

## 索引优化建议

### 创建索引原则

| 原则 | 说明 |
|------|------|
| 选择区分度高的列 | 区分度越高，索引效果越好（可用 `COUNT(DISTINCT col)/COUNT(*)` 评估） |
| 索引不是越多越好 | 索引占用额外空间，影响写操作性能（INSERT/UPDATE/DELETE） |
| 利用最左前缀原则 | 复合索引从左到右使用，避免索引失效 |
| 覆盖索引优先 | 让索引包含查询所需全部字段，减少回表 |

### 高频面试题

**Q1: 聚簇索引 vs 非聚簇索引**

| 特性 | 聚簇索引 | 非聚簇索引 |
|------|----------|------------|
| 数据存储 | 叶节点存储完整数据行 | 叶节点存储索引值和主键 |
| 查询方式 | 主键查询直接定位数据 | 先查索引，再回表查数据 |
| 插入性能 | 主键自增时插入快 | 无影响 |
| 空间占用 | 一个表一个 | 可以有多个 |
| 适用场景 | 主键查询、范围查询 | 高频查询字段 |

**Q2: 主键索引 vs 唯一索引**

| 特性 | 主键索引 | 唯一索引 |
|------|----------|----------|
| 约束 | 唯一且非空 | 唯一但可为空 |
| 数量 | 一个表只能一个 | 可以有多个 |
| 自动创建 | 表创建时自动 | 手动创建 |
| 索引结构 | 聚簇索引 | 非聚簇索引 |

**Q3: 复合索引的最左前缀原则**

假设有复合索引 `(name, age, gender)`：

```sql
-- ✅ 走索引（使用最左前缀）
SELECT * FROM users WHERE name = 'Alice';
SELECT * FROM users WHERE name = 'Alice' AND age = 25;

-- ❌ 不走索引（跳过最左列）
SELECT * FROM users WHERE age = 25;
SELECT * FROM users WHERE gender = 'F';
```

**Q4: 索引下推（Index Condition Pushdown, ICP）**

**作用**：在复合索引中，在索引遍历过程中就过滤数据，减少回表次数

**条件**：
- 适用于 `WHERE` 条件中包含索引列
- 用于 `range`、`ref`、`eq_ref`、`ref_or_null` 访问类型

**示例**：
```sql
-- 假设有索引 (name, age)
SELECT * FROM users WHERE name LIKE 'A%' AND age = 25;

-- 无 ICP：先根据 name 找到所有匹配的行，再回表检查 age
-- 有 ICP：在索引遍历时直接过滤 age = 25，减少回表次数
```

**Q5: 索引失效如何排查**

1. 使用 `EXPLAIN` 查看执行计划
2. 检查 `type` 列：ALL = 全表扫描
3. 检查 `key` 列：是否使用了索引
4. 检查 `Extra` 列：是否有 `Using filesort`、`Using temporary`、`Using index condition`

**Q6: 为什么 MongoDB 选 B 树而 MySQL 选 B+ 树**

| 对比 | MongoDB（B 树） | MySQL（B+ 树） |
|------|------------------|----------------|
| 数据存储 | 每个节点都存储数据 | 只有叶子节点存储数据 |
| 查询复杂度 | 最好 O(1)，最坏 O(log n) | 稳定 O(log n) |
| 范围查询 | 需要遍历所有节点 | 叶子节点链表连接，顺序遍历快 |
| 磁盘 I/O | 不稳定，可能多次 I/O | 稳定，可预估 I/O 次数 |

**Q7: 一条 SQL 是如何执行的**

```sql
SELECT * FROM users WHERE id = 1;
```

**执行流程**：
1. **连接器**：验证用户身份，建立连接
2. **查询缓存**：8.0 已移除（命中率低）
3. **分析器**：词法分析、语法分析
4. **优化器**：生成执行计划，选择索引
5. **执行器**：调用存储引擎接口执行
6. **存储引擎**：InnoDB 从磁盘读取数据页到内存

**Q8: count(*) vs count(1) vs count(字段)**

| 方式 | 说明 | 性能 |
|------|------|------|
| count(*) | 统计所有行数，包含 NULL | ✅ 最优 |
| count(1) | 统计所有行数，忽略 NULL | 略逊 |
| count(字段) | 统计非 NULL 行数 | 最差 |

**InnoDB 优化**：count(*) 和 count(1) 实际上没有区别，InnoDB 会选择最小的索引来扫描
