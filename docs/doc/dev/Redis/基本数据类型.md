## 一句话速览

Redis 的 5 种基本类型不是 5 种数据结构，而是 5 种**对外接口**：每种类型内部都会按数据规模和元素特征，在「紧凑型结构」和「性能型结构」之间自动切换编码 —— 用小数据换内存、大数据换速度。

| 类型 | 存什么 | 有序 | 可重复 | 小数据编码 | 大数据编码 | 转换触发 |
| --- | --- | --- | --- | --- | --- | --- |
| String | 字符串 / 整数 / 浮点数，≤ 512 MB | — | — | `int` / `embstr` | `raw` | 非长整型且长度 > 44 字节 |
| List | 有序元素序列 | 是（插入序） | 是 | `quicklist`（节点为 listpack） | `quicklist`（节点为 ziplist） | 3.2 前：> 512 个 或 任一元素 ≥ 64 字节 |
| Hash | 字段 → 值 | 否 | 字段唯一 | `ziplist`，7.0 起 `listpack` | `hashtable` | > 512 对 或 任一字段/值 ≥ 64 字节 |
| Set | 唯一成员集合 | 否 | 否 | `intset`（全整数时） | `hashtable` | 含非整数 或 > 512 个 |
| Zset | member + score，按 score 排序 | 是（score 序） | member 唯一，score 可重复 | `ziplist`，7.0 起 `listpack` | `skiplist` + `hashtable` | > 128 个 或 任一 member ≥ 64 字节 |

> 上面所有阈值都来自 `redis.conf`，可以按业务调：`hash-max-listpack-entries`、`zset-max-listpack-entries`、`set-max-intset-entries` 等（7.0 前叫 `*-max-ziplist-*`）。

## 五大数据类型

### String（字符串）

String 是 Redis 最基础的类型，值可以是字符串、整数或浮点数，**最大 512 MB**。它是二进制安全的，可以存文本、图片序列化数据等任意字节流；支持原子自增自减（`INCR` / `DECR`），天然适合计数场景。

底层编码按值的类型和长度三选一：

| 编码 | 触发条件 | 内存布局 |
| --- | --- | --- |
| `int` | 值可以用 long 表示 | 直接把整数存进 `redisObject` 的 `ptr` 字段，不额外分配 SDS |
| `embstr` | 长度 ≤ 44 字节（非整数） | `redisObject` 与 `sdshdr` **一次分配、连续存放** |
| `raw` | 长度 > 44 字节（非整数） | `redisObject` 与 `sdshdr` **两次分配**，用指针指向 |

两种 SDS 布局的差别，就是「分配次数」带来的连锁差异：

- **embstr**：一次 `malloc` 拿到整块内存，创建/释放各一次调用，布局紧凑、碎片少，且数据连续更利于 CPU 缓存命中 —— 专为短字符串优化。
- **raw**：两次独立分配，指针跳转访问，更灵活但开销略大、数据不连续。

> ⚠️ 任何对 `embstr` 的**修改操作**（如 `APPEND`、`SETRANGE`）都会先把它转成 `raw`，**不管改完是否还在 44 字节内** —— 因为 embstr 的内存是只读式的一整块，无法原地扩容。

**44 这个数字怎么来的**：不是拍的，是凑 64 字节分配单元算出来的。

```
redisObject(16) + sdshdr8 头(3) + 字符串内容(N) + 结尾 \0(1) ≤ 64
⇒ N ≤ 64 - 16 - 3 - 1 = 44
```

`sdshdr8` 是 Redis 3.2 优化后的短字符串头，只用 3 字节。超过 44 字节就要跨出 64 字节的常用分配单元，「一次分配大块连续内存」的收益随之下降，于是改为 `raw`。

### List（列表）

List 是**有序、可重复**的元素序列，支持从头部（左）或尾部（右）插入弹出，两端操作都是 O(1)，可以当栈、队列、阻塞队列用。

底层实现经历过一次换代：

| 版本 | 实现 | 规则 |
| --- | --- | --- |
| < 3.2 | `ziplist` / `linkedlist` | 所有元素长度 < 64 字节 **且** 元素数 < 512 → `ziplist`，否则 `linkedlist` |
| ≥ 3.2 | `quicklist` | 统一用「多个 ziplist 串成的双向链表」 |
| ≥ 7.0 | `quicklist` + `listpack` | 链表节点内的 ziplist 被 listpack 取代 |

`quicklist` 是 `ziplist` 的内存紧凑 + `linkedlist` 的节点修改效率的结合体。7.0 把节点换成 `listpack`，是为了解决 `ziplist` 在极端情况下可能引发的**连锁更新**问题。

### Hash（哈希）

Hash 是键值对集合，适合存对象（如用户信息的一个个字段），单个 Hash 最多可存 **40 多亿**个键值对。

| 编码 | 触发条件 | 说明 |
| --- | --- | --- |
| `ziplist`（< 7.0）/ `listpack`（≥ 7.0） | 所有字段和值的长度 < 64 字节 **且** 键值对数量 < 512 | 紧凑存储，省内存 |
| `hashtable` | 任一条件不满足 | 保证大数据量下的 O(1) 查询 |

> 编码转换是**单向的**：一旦升级为 `hashtable`，即使后续删到只剩几条数据，也不会退回 `ziplist` / `listpack`。

### Set（集合）

Set 是**无序、不重复**的字符串集合，支持交、并、差集运算，常用于去重、共同好友、标签。

| 编码 | 触发条件 | 说明 |
| --- | --- | --- |
| `intset` | 所有元素都是整数 **且** 数量 ≤ 512 | 整数集合，紧凑且二分查找 |
| `hashtable` | 含非整数元素，或数量 > 512 | 每个元素作键，值统一为 `NULL` |

### Zset（有序集合）

Zset 是 Set 的扩展，每个 member 绑一个 score，按 score 排序；member 唯一但 score 可重复。典型场景是排行榜、延时队列。

| 编码 | 触发条件 | 说明 |
| --- | --- | --- |
| `ziplist`（< 7.0）/ `listpack`（≥ 7.0） | 元素数 < 128 **且** 所有 member 长度 < 64 字节 | 小集合紧凑存储，按 score 顺序排列 |
| `skiplist` + `hashtable` | 任一条件不满足 | 跳表维护 score 有序 + 支持范围查询；哈希表提供 O(1) 的 member → score 查找 |

> 为什么大数据量要**两个结构一起用**：跳表擅长范围与排序但按 member 查 score 是 O(log N)，哈希表按 member 查 score 是 O(1) 却不维护顺序，两者互补。代价是同一份数据存两遍。

### 编码规律的共同点

五类类型其实是同一条设计哲学的五个实例：

- **小数据走紧凑结构**（SDS 短串 / ziplist / listpack / intset）：连续内存、无指针、省内存，代价是修改可能触发整体重分配。
- **大数据走性能结构**（raw / hashtable / quicklist / skiplist）：指针多、内存开销大，但插入删除和查找稳定 O(1)~O(log N)。
- **编码只升不降**：`embstr → raw`、`intset → hashtable`、`ziplist → hashtable`、`listpack → skiplist`，全部单向，避免在边界值上反复抖动。

## 底层数据结构

各类类型最终都落到这 7 个结构上：

| 结构 | 定位 | 服务于 | 一句话 |
| --- | --- | --- | --- |
| SDS | 动态字符串 | String | 带长度字段的字节数组，二进制安全 |
| Intset | 整数有序集合 | Set | 升序排布的整数数组，支持类型升级 |
| Ziplist | 压缩列表 | 旧版 Hash / List / Zset | 连续内存 + 每项记录前驱长度，省内存但有连锁更新风险 |
| Listpack | 紧凑列表 | 7.0+ Hash / List / Zset | 每项记录自身长度，消除连锁更新 |
| Quicklist | 快速列表 | List | 双向链表，每个节点是一个 ziplist / listpack |
| Hashtable（dict） | 哈希表 | Hash / Set / Zset / 全局键空间 | 链地址法 + 渐进式 rehash |
| Skiplist | 跳跃表 | Zset | 多级索引实现 O(log N) 有序访问 |

### 简单动态字符串（SDS）

SDS 是 Redis 为替代 C 原生字符串而实现的字符串结构，二进制安全，可存任意数据（包括 `\0`）。

**结构设计**：三个关键字段 —— `len` 记录已用字节数、`alloc` 记录分配的总容量、`buf` 字节数组存实际内容。

**核心优势**：

| 优势 | 实现方式 |
| --- | --- |
| O(1) 取长度 | 直接读 `len`，C 字符串要 O(N) 遍历 |
| 杜绝缓冲区溢出 | 修改前检查 `alloc - len`，不足则自动扩容 |
| 减少内存重分配 | **空间预分配**（扩容多给冗余）+ **惰性空间释放**（缩短不立即还内存） |
| 二进制安全 | 以 `len` 判断结尾而非 `\0`，可存二进制数据 |

### 整数集合（Intset）

当 Set 的元素全是整数且数量不多时，用 intset 存储 —— 紧凑、有序、省内存。

```c
typedef struct intset {
    uint32_t encoding;  // 编码方式
    uint32_t length;    // 元素个数
    int8_t contents[];  // 柔性数组，升序且唯一
} intset;
```

`encoding` 决定单个元素占几位：`INTSET_ENC_INT16`（2 字节）、`INTSET_ENC_INT32`（4 字节）、`INTSET_ENC_INT64`（8 字节）。

#### 类型升级机制

新元素超出当前编码范围时自动升级，分三步：

1. **空间分配**：按新编码算好总长度，重新分配 `contents`
2. **元素迁移**：从后向前把旧元素逐个转成新编码，放到正确位置（倒序搬，避免覆盖）
3. **插入新元素**：新元素只可能在头部或末尾，直接放进去

例：`[1, 3, 5]` 用 16 位编码，插入 50000（超 32767）后整体升级到 32 位再插入。

> 升级后**不支持降级** —— 即使把大数删掉，编码也不会缩回去。

#### 核心操作

| 操作 | 复杂度 | 做法 |
| --- | --- | --- |
| 查找 | O(log N) | 先判空、再判范围，最后二分查找 |
| 插入 | O(N) | 判断是否需要升级 → 二分定位 → 扩容并后移元素 → 写入 |
| 删除 | O(N) | 删除后需**前移元素**填补空隙，维持内存连续 |

### 压缩列表（Ziplist）与列表包（Listpack）

两者都是为「少量、小尺寸」数据设计的紧凑顺序结构，把一整块内存当数组用。

**Ziplist 结构**：`zlbytes`（总字节数）→ `zltail`（尾节点偏移）→ `zllen`（节点数）→ 多个 `entry` → `zlend`（结束标记）。每个 `entry` 记录三样东西：**前一个节点的长度**（`prevlen`）、自身编码方式、自身内容。

**Listpack 的改进**：Redis 7.0 用来取代 ziplist，核心是**消除连锁更新**。

> **连锁更新**：ziplist 里 `prevlen` 字段是变长的（前驱 < 254 字节用 1 字节，否则 5 字节）。一旦某个节点变长导致下一节点的 `prevlen` 从 1 字节涨到 5 字节，就可能继续撑大再下一个…… 最坏情况整条列表每个节点都要重新分配。Listpack 让每个节点**记录自身长度**而非前驱长度，节点之间彻底解耦，问题消失。

**用在哪**：旧版本小型 Hash / List / Zset 都用 ziplist；现在 List 和 Hash 在数据量小时用的是基于 listpack 的 quicklist。

### 快速列表（Quicklist）

List 从 3.2 起的默认实现，是 ziplist 与 linkedlist 的混合体。

**结构**：外层是双向链表，**每个链表节点是一个 ziplist（7.0 起是 listpack）** —— 可以理解成「由多个小 ziplist 串成的链表」。

**设计权衡**：

| 极端方案 | 问题 |
| --- | --- |
| 纯 linkedlist | 每个元素一次独立分配 + 两个指针，内存碎片多、指针开销大 |
| 纯超大 ziplist | 修改可能触发整体重分配与连锁更新，且内存必须连续 |
| **quicklist** | 控制每个节点的大小，兼顾内存局部性与插入性能 |

### 哈希表（Hashtable / dict）

Redis 的哈希表用**链地址法**解决冲突（思路同 Java 的 HashMap）：哈希到同一数组下标（桶）的键值对，用 `next` 指针串成链表。冲突处理始终是链地址法；Redis 7.0 只是为「无值字典」（Set 底层）引入了 `dictEntryNoValue`，省掉一个 value 指针。

三层结构体：

```c
typedef struct dict {
    dictht ht[2];    // 两个哈希表，用于渐进式 rehash
    long rehashidx;  // rehash 进度指示器，-1 表示未进行
    // ... 类型特定函数等其他字段
} dict;
```

```c
typedef struct dictht {
    dictEntry **table;      // 桶数组
    unsigned long size;     // 桶的数量
    unsigned long sizemask; // 大小掩码，恒等于 size - 1
    unsigned long used;     // 已有节点数
} dictht;
```

```c
typedef struct dictEntry {
    void *key;
    union {
        void *val;
        uint64_t u64;
        int64_t s64;
        double d;
    } v;                    // 联合体：可存指针，也可内嵌数值省一次分配
    struct dictEntry *next; // 冲突链
} dictEntry;
```

#### 渐进式 Rehash

扩容或收缩时，Redis **不一次性搬完** `ht[0] → ht[1]`，而是把迁移成本摊到后续每次读写上，避免长时间阻塞。

**触发条件**：

| 方向 | 条件 |
| --- | --- |
| 扩容 | 未执行 BGSAVE / BGREWRITEAOF 时，负载因子 `used/size` ≥ 1；或负载因子 ≥ 5（数据太满，即使正在持久化也强制扩容） |
| 收缩 | 负载因子 < 0.1 |

**执行步骤**：

1. **分配空间**：给 `ht[1]` 分配第一个 ≥ `ht[0].used * 2`（扩容）或 ≥ `ht[0].used`（收缩）的 2 的 N 次幂
2. **开启标记**：`rehashidx` 从 -1 设为 0
3. **分批迁移**：之后每次增删改查，除了执行本命令，还顺带把 `ht[0]` 在 `rehashidx` 位置整个桶的节点搬到 `ht[1]`，然后 `rehashidx++`
4. **收尾**：搬完后释放 `ht[0]`，`ht[1]` 变成新的 `ht[0]`，再给 `ht[1]` 建一张空表，`rehashidx` 复位为 -1

**期间的行为**：

- 查找 / 删除 / 更新：**先查 `ht[0]`，再查 `ht[1]`**，两边都动
- 新增：**只写 `ht[1]`**，保证 `ht[0]` 的节点数只减不增，最终一定会搬空

### 跳跃表（Skiplist）

Zset 的核心结构之一，用多级索引把查找、插入、删除做到平均 O(log N)，实现比红黑树简单得多。

**结构**：

- `zskiplist`：头节点指针、尾节点指针、最大层数、长度
- `zskiplistNode`：`member`（元素）、`score`（分值）、`backward`（后退指针，支持反向遍历）、`level[]` 数组（每层含**前进指针**和**跨度 span**）

**工作原理**：高层是稀疏索引相当于「快速通道」，底层链表存放全量数据。查找从最高层出发，能往前就往前，走不动就下沉一层，从而跳过大量节点。`span` 用于 O(log N) 计算排名（`ZRANK`）。

**与哈希表配合**：跳表负责按 score 排序与范围查询，哈希表负责 O(1) 的 member → score 定位，两个索引指向同一份数据。

### 链表（LinkedList）

标准的**双向无环链表**，每个节点持有前驱和后继指针。

**特点**：结构体维护头指针、尾指针、长度计数器，所以取长度、头尾增删都是 O(1)。

**缺点**：每个节点独立分配内存（值 + 两个指针），内存碎片多、开销大。

**现状**：仅作为历史结构存在 —— 3.2 之前 List 在元素较多或较大时用它，之后被 `quicklist` 取代。
